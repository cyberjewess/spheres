Instagram-Stories-style post composer: pick a base photo, stack text and image layers on top, drag/resize/rotate each one, then flatten to a single image and post it to a Sphere. Mobile-first — most usage will be through a phone browser.

Today `Post` is text-only (`title`, `content` — see `prisma/schema.prisma`) and there is no image upload, canvas, or blob storage anywhere in the repo. This is a greenfield feature, not an extension of an existing pattern.

# Tech approach (decided)

- **Rendering: Konva.js** (canvas scene graph), not DOM+CSS-transform flattened with html2canvas/dom-to-image. Konva gives native drag/resize/rotate via `Konva.Transformer` and exports the exact same draw calls it renders on screen (`stage.toBlob()`), so there's no separate "flatten the DOM" step that can drift from what the user saw (fonts, gradients, Safari quirks are the usual culprits there).
- **Svelte binding: pin `svelte-konva@0.3.1`.** The `^1.x` line of `svelte-konva` is runes-only and requires Svelte 5 — this app is Svelte 4, so installing latest would break. If the wrapper's reactivity fights the 60fps gesture updates during drag/pinch, fall back to driving vanilla Konva imperatively in `onMount`/`onDestroy` and use Svelte stores only as the serializable model (synced on gesture-end, not every frame).
- **Storage: Vercel Blob** for now, client-direct upload. Avoids Vercel's 4.5MB serverless request-body cap and gives a CDN URL to store in Postgres, instead of base64-in-column bloat. Isolated behind a small storage-adapter interface (see Phase 0) so swapping to R2/S3/Cloudinary later is a new adapter file, not a rewrite.
- **Fonts:** small curated self-hosted OFL (`.woff2`) set (5-8 fonts), not an open Google-Fonts picker. Must gate first draw/export on `document.fonts.ready` / per-font `.load()` — canvas `fillText` silently uses whatever font is loaded *at draw time*, and once exported to pixels a fallback-font render can't be fixed after the fact.
- **Gesture math:** Konva's `Transformer` handles handle-drag resize/rotate out of the box. Two-finger pinch+twist (resize+rotate together, the core IG-story gesture) is not built in — hand-roll it from Konva's documented multi-touch recipe (~50 lines: two-touch distance → scale, two-touch angle → rotation) rather than pulling in Hammer.js (stagnant) or interact.js (fine as a fallback if the hand-rolled math is too fiddly).
- **Bundle:** Konva is ~50KB gzipped — keep it out of the main bundle by importing only inside the editor route's component (or dynamic `import()` in `onMount`), guarded by `browser` from `$app/environment` (it's canvas/`window`-dependent, so it must be client-only anyway).

### Post-Phase-7 fix: Konva was wiping the Svelte-rendered overlays

**Found by a real Playwright run against a real Postgres DB and real headless Chromium** — the first time this feature was exercised in an actual browser, not just `tsc`/`svelte-check`/`vitest`/`vite build`. None of those would have caught this: it's a DOM-mutation-order bug at runtime, not a type or logic error.

`create-story/+page.svelte`'s `stage-wrapper` div (bound as `stageWrapperEl`) was being passed directly to `StoryCanvasController.create(stageWrapperEl, ...)` as Konva's stage container — but that same div was *also* where Svelte rendered the "choose a photo" prompt (`{#if !hasBaseImage}`) and the floating trash/duplicate toolbar (`{#if selectionRect && ...}`) as direct sibling children. `node_modules/konva/lib/Stage.js`'s `_buildDOM()` (called from the `Konva.Stage` constructor) does `container.innerHTML = '';` unconditionally before inserting its own `.konvajs-content` div — wiping whatever the given container already held. Since the Stage is constructed in `onMount`, i.e. *after* Svelte's initial render already put the "Choose photo" prompt in the DOM, that prompt (and its Svelte-internal anchor nodes) was destroyed the instant the canvas mounted — there was no way to ever pick a base photo in a real browser, and the floating toolbar would have suffered the same fate whenever it needed to appear.

**Fix**: Konva now gets its own dedicated, Svelte-untouched leaf element (`konva-container`, `position: absolute; inset: 0` so it still fills `stage-wrapper` exactly) nested *inside* `stage-wrapper` rather than being handed `stage-wrapper` itself. `stageWrapperEl` is kept (and still bound) purely for its `clientWidth`/`clientHeight` reads in `computeFloatingToolbarStyle` and as the positioning context for the overlays — only the element passed to `StoryCanvasController.create()` changed, from `stageWrapperEl` to a new `konvaContainerEl`. No coordinate math anywhere else needed to change, since `selectionRect`/drag positions were already in stage-local pixels and `konva-container`'s CSS guarantees it's pixel-identical in size/position to `stage-wrapper`.

**Side effect caught while applying the fix, not left for QA to find twice**: giving `.konva-container` `position: absolute` means it's now a *positioned* element — CSS paints positioned elements above non-positioned in-flow siblings regardless of DOM order. `.pick-base-photo` wasn't positioned (it only used `margin: auto` for flex-centering), so without a further fix the (empty, but still painted) Konva canvas would have visually covered the "Choose photo" prompt even after the wipe bug itself was fixed. Given `.pick-base-photo` its own `position: relative; z-index: 1` (above `.konva-container`'s explicit `z-index: 0`) so it stacks correctly. `.floating-toolbar` already had `position: absolute; z-index: 50` from Phase 4, so it was unaffected.

**How this was checked without live browser access**: read `node_modules/konva/lib/Stage.js` directly to confirm the exact `container.innerHTML = ''` call and that it operates on whatever object is passed as `container` in the Stage constructor options (not on some ancestor) — then confirmed `konvaEditor.ts`'s `this.container` is exactly that same reference, and that the fixed template places `konva-container` as an *empty* leaf `<div>`, a sibling of (never an ancestor of) the `{#if}` overlay blocks — so there is no template structure by which the overlays' content could end up inside the element Konva wipes. Followed by the full `tsc`/`svelte-check`/`vitest`/`vite build` loop (all clean, zero new errors) to confirm nothing else regressed.

### Post-Phase-7 adversarial review: 10 confirmed bugs, all fixed

An adversarial pre-PR review (9 independent finder agents across correctness/reuse/simplification/efficiency/altitude angles, each candidate re-verified by a separate agent pass) found 10 real, confirmed bugs across the feature. All 10 are now fixed:

1. **Broken access control** (`create-story/+page.server.ts`) — `createStoryPost` accepted any `sphere` id from form data with no check it belonged to the requester; any logged-in user could post into a Sphere they didn't own. Fixed: re-verify `Number(sphere)` against `prisma.sphere.findFirst({ where: { id, userId: user.id } })`, `fail(403, ...)` if not owned.
2. **Unvalidated `imageUrl`** (same file) — accepted verbatim from form data with no check it pointed at our own storage. Fixed: added `StorageAdapter.isOwnUrl(url)` (checks the Vercel Blob public-URL hostname suffix, not a hardcoded store id — stays provider-swappable), called before accepting the URL.
3. **Font-loaded export check verified the wrong weight** (`fonts.ts`) — always checked/loaded weight 700 regardless of what Konva actually renders (always normal/400, since no weight is ever set on the Text node). Fixed: check weight 400, matching what's actually drawn.
4. **Pinch gesture didn't know about active text-editing** (`konvaEditor.ts`) — a two-finger touch while a text layer's textarea overlay was open would silently transform the hidden node underneath. Fixed: `handleTouchStart` bails if `activeTextEdit` is set; `enterTextEditMode` also bails if a pinch is in progress.
5. **`updatePost` hardcoded `sphereId: 1, userId: 1` with zero ownership check** (`[postId]/+page.server.ts`, pre-existing but newly exercised by Story posts reaching real, non-default Spheres/owners through the same edit form) — fixed: removed the hardcoded ids from the update entirely (an edit changes title/content, never which Sphere/owner a post belongs to), and added a real ownership check in both `load` and `updatePost` (403 if the post isn't the requester's).
6. **Base image never refit on resize** (`konvaEditor.ts`) — `handleResize()` called `fitBaseImage()` with no argument, so it silently no-op'd. Fixed: `this.fitBaseImage(this.lastState ?? undefined)`.
7. **Orphaned textarea + undo-stack pollution on layer delete mid-edit** (`konvaEditor.ts`) — the destroy loop in `syncLayers` didn't check `isBeingEdited` before destroying a node, orphaning its textarea overlay. Fixed: added `discardActiveTextEdit()`, called before destroying a node whose layer is mid-edit.
8. **Async controller create/destroy race (leak)** (`create-story/+page.svelte`) — `StoryCanvasController.create()` is async; unmounting before it resolved meant the controller was never destroyed. Fixed: a `destroyed` flag checked in the `.then()` callback destroys the controller immediately if the component already unmounted.
9. **`deleteImage` never wired up** — implemented but never called; `deletePost` left every deleted story's blob orphaned in storage forever. Fixed: `deletePost` now calls `storage.deleteImage(imageUrl)` (best-effort, doesn't block the already-succeeded row deletion on a storage-provider hiccup).
10. **Unguarded `request.json()`** (`api/upload/+server.ts`) — sat outside the route's `try/catch`, so a malformed body caused an unhandled 500 instead of a clean 400. Fixed: moved inside the `try` block.

**Verification**: `tsc`/`svelte-check`/`vitest`/`vite build` all clean (zero new errors; one *fewer* pre-existing tsc error than baseline, since fixing `[postId]/+page.server.ts`'s `load` type incidentally resolved its own implicit-any too). Added `tests/story-editor-access-control.spec.ts` — two new real E2E regression tests against a live Postgres DB, confirming a second user genuinely cannot post into the first user's Sphere (403), and a non-Vercel-Blob `imageUrl` is genuinely rejected (400). Both pass. Note for future reference: SvelteKit responds to a `fetch`-style POST (e.g. Playwright's `page.request.post()`) with a JSON envelope (`{"type":"failure","status":N,...}`) at HTTP 200, not a raw HTTP status code — only a genuine full-page browser form navigation gets the raw status; tests asserting on action failures need to parse that envelope. Also: SvelteKit's CSRF protection rejects a raw `page.request.post()` unless it sets an `Origin` header matching the site.
